0. NON-NEGOTIABLE ARCHITECTURAL DIRECTIVE — FLEXIBLE CANON + AUTOMATIC VERSION REPLACEMENT

STOP. THIS IS A CORE ARCHITECTURAL REQUIREMENT, NOT AN OPTIONAL FEATURE.

IDSS EGE MUST BE DESIGNED FROM DAY ONE AS A FLEXIBLE, VERSIONED, CANONICAL-SOURCE-DRIVEN SYSTEM. The application must never depend on developers manually changing code whenever the competent ministry publishes a new catalogue, law, regulation, rulebook, official form, decision, instruction, examination document or other authoritative material.

The Director / Superadmin account direktor@idss.ba must be able, through the secure Superadmin Control Panel, to upload a new official document and make it the active canonical version for its document type and subject. The application must then automatically stop using the previous version for current operation and use the newly published/approved version as the active source.

CODE MUST NOT HAVE TO CHANGE FOR NORMAL CANON UPDATES. A future ministry update must be handled through data/content administration, not through a developer deployment, provided the underlying document type and application capabilities remain compatible.

CANON UPDATE LIFECYCLE — MANDATORY
  1. The Director receives an official ministry publication/document: catalogue, law, regulation, rulebook, decree/decision, official form, instruction, examination specification or other authoritative source.
  2. The Director opens the relevant Superadmin area and uploads the new document.
  3. The Director records or confirms its metadata: document type, subject/scope, issuing authority, official title, publication/effective date, source/reference, version or revision identifier where available, and status.
  4. The system validates the file, stores the original immutable source, creates a new canonical version and preserves complete provenance.
  5. The system processes the new source into the appropriate structured knowledge representation without silently changing its meaning.
  6. After successful validation/publish, the new version becomes ACTIVE for the relevant scope.
  7. The previous active version becomes SUPERSEDED / INACTIVE automatically. It must no longer drive current student practice, current exam rules or current official document generation.
  8. The previous version must not be hard-deleted. Historical versions, provenance, audit records and previously generated artefacts must remain traceable for accountability, debugging and historical reporting.
  9. The system must invalidate/rebuild affected caches, indexes, derived learning objects and current-content references so that users do not continue receiving stale canonical content.
  10. The system must record who published the new version, when, what it replaced, what processing occurred and whether validation succeeded.
NO HARD-CODED CANONICAL CONTENT

Do not hard-code examination rules, catalogue questions, official forms, legal wording, scoring structures, subject requirements or document-specific business rules into React/Vue components, static JSON files, constants or other code when those facts can change through an official publication.

Build the application so that code defines the engine; canonical documents define the current authoritative content and rules. The system must therefore separate application logic from canonical content and from derived learning representations.

Required Canonical Version Model

At minimum, the architecture must distinguish:

  • Document Type — e.g. German exam catalogue, Mathematics exam catalogue, Bosnian exam catalogue, law, regulation, rulebook, official form, decision, instruction.
  • Document Version — immutable uploaded source plus metadata and checksum/hash.
  • Scope — subject, grade, exam, document category or other applicable scope.
  • Status — draft, processing, validation-required, active, superseded, archived, rejected.
  • Effective Date / Publication Date — where supplied by the authority.
  • Provenance — issuing authority, official title, source location, uploader, timestamp, verification status.
  • Derived Content — structured questions, competencies, topics, rules, forms, mappings and other machine-readable representations derived from the source.
  • Dependency Map — which application features and generated artefacts depend on which canonical version.

Active content must always resolve through the current active canonical version, never through a stale hard-coded reference.

SEMANTIC INTEGRITY IS MORE IMPORTANT THAN SIMPLE FILE UPLOAD.

An uploaded PDF is not considered successfully integrated merely because it is stored in the database/storage bucket. The system must extract, structure, validate, index and connect its meaningful content to the appropriate application model. If a new catalogue replaces an old catalogue, the relevant questions, topics, competencies, rules and exam structures must be regenerated or revalidated from the new source.

CATALOGUE QUESTION INGESTION — MINIMUM 200 QUESTIONS PER SUBJECT

During the initial build, ACA must fully process all catalogue questions contained in the canonical examination documents for each of the three subjects — Bosnian language, Mathematics and German language — with a validation target of at least 200 catalogue questions per subject where the authoritative source provides them.

Do not treat this as bulk PDF text extraction. Every question must be understood and represented at the levels of syntax, logic and semantics before it becomes trusted application content.

Syntax

Preserve the exact wording, punctuation, numbering, answer-option structure, mathematical notation, language-specific characters, units, symbols and relevant formatting. Do not paraphrase the canonical question in place of the original.

Logic

Determine what the task actually asks the student to do: required operations, constraints, relationships, dependencies, expected reasoning path, answer conditions and—only when supported by the source—correct answer or scoring logic.

Semantics

Identify the educational meaning: subject, domain, topic, competency, concept, skill, knowledge type, task intent and relevant canonical requirement. Semantic interpretation must remain traceable to the source and must never invent unsupported meaning.

Mandatory Structured Representation of Every Catalogue Question

Each imported question should have, as applicable:

  • stable question ID;
  • subject;
  • canonical document ID and exact document version;
  • page / section / source location;
  • original question number;
  • exact canonical text;
  • normalized machine-readable text where necessary, while preserving the original;
  • answer options and exact option structure, when present;
  • syntax representation;
  • logic/task representation;
  • semantic representation;
  • topic/domain/competency mappings;
  • task type;
  • difficulty or cognitive-demand classification only when defensibly derived and clearly marked as derived;
  • answer/scoring information only when actually supported by the authoritative source;
  • validation status;
  • parser/extraction provenance;
  • last verified timestamp and verifier/process information.
QUALITY GATE FOR CATALOGUE INGESTION

ACA must produce an auditable ingestion report showing, per subject: number of source pages processed, number of questions detected, number successfully structured, number requiring manual review, duplicate/near-duplicate findings, missing or ambiguous elements, and final validation status. If the source contains fewer than 200 questions, do not invent questions to reach 200. Report the actual authoritative count and the discrepancy.

No catalogue question may enter the trusted question bank merely because OCR/parser extraction succeeded. Structural validation and semantic/source validation are separate gates.

2. Mission

Build IDSS EGE, a secure, maintainable, source-traceable educational web application for Grade 9 students and IDSS staff preparing for the Sarajevo Canton external matriculation examination.

THREE-SUBJECT RULE — ABSOLUTE

IDSS EGE prepares Grade 9 students for the three teaching subjects prescribed for the external matriculation examination: Bosnian language, Mathematics and German language.

These three subjects are the core academic scope of the student experience. Do not add, remove, substitute or invent an examination subject. Do not create a fourth exam subject, an alternative subject track or a generic multi-subject LMS model unless the CANON itself is officially updated and the change is explicitly reflected in the repository.

The exact official names, scope, structure, competencies, requirements, scoring, tasks, formats and other examination rules must always be taken from the current canonical documents in the EGE repository. The application must never rely on memory, generic knowledge or assumptions where the CANON provides the answer.

The product has two simultaneous identities:

  • For students: a game-first learning environment that exists first and foremost for the students and their successful, structured preparation in Bosnian language, Mathematics and German language.
  • For teachers and school support staff: a serious academic support and monitoring platform that enables teachers, pedagogues and psychologists to follow each student's progress in detail and use practical intervention/support tools.
  • For school leadership: a secure institutional oversight platform providing useful aggregate information, configuration, audit and reporting without unnecessary exposure of sensitive student data.

The application is not a generic LMS, document library, quiz app, school portal or dashboard. It is a canonical-source-driven exam preparation platform with a game-first student experience.

Destructive deletion must be controlled, auditable and compatible with applicable retention/privacy requirements.

7A.5 Authentication & Authorization

  • Username + password for every user.
  • Never store plaintext passwords.
  • Use a modern password-hashing algorithm and secure credential handling.
  • Protect against brute force, credential stuffing, session fixation, session theft and account enumeration.
  • Use secure sessions/tokens, appropriate expiry and secure cookies where applicable.
  • Enforce RBAC/ABAC server-side and, where supported, at database/data-access level.
  • Frontend visibility is never a substitute for authorization.
  • All sensitive administrative actions must be auditable.

7A.6 GDPR / Privacy-by-Design

Design the platform around data minimization, purpose limitation, least privilege, access control, retention rules, auditability and secure processing. Do not collect or infer personal/sensitive information merely because it might be technically possible.

  • Separate academic progress from sensitive support/psychological records.
  • Limit access by role, scope and legitimate institutional purpose.
  • Do not infer diagnoses, mental states, intelligence, personality or motivation from usage telemetry.
  • Provide controlled correction/deletion/export mechanisms where required by applicable law and institutional policy.
  • Document what data is stored, why it is stored, who may access it and how long it is retained.

7A.7 Security Engineering — Design Against Real Threats

The system must be designed and tested against common web/application threats, including injection, XSS, CSRF where applicable, insecure direct object references, privilege escalation, broken access control, malicious uploads, secret leakage, unsafe dependencies, API abuse, rate-limit bypass and prompt injection against AI features.

  • Secure HTTP headers and transport.
  • Strict input validation and output encoding.
  • Parameterized database access/ORM protections.
  • File type, size and content validation; safe storage and processing.
  • Rate limiting and abuse controls.
  • Dependency and vulnerability auditing.
  • No hard-coded secrets.
  • Security logging and alertable events.
  • Regular automated security tests plus targeted manual verification.

11. Student Support Mission — Teachers, Pedagogue & Psychologist

The application exists because of the students.

Every staff-facing function must ultimately answer one question: How does this help us give this student better support?

Teachers, the pedagogue and the psychologist must have carefully designed, genuinely useful tools for following the progress of each individual student across the three exam subjects and for understanding where support may be needed.

Staff tools should support, where justified by role and data:

  • individual student progress;
  • subject-by-subject progress;
  • topic and competency performance;
  • practice history;
  • persistent error patterns;
  • completed and missed missions/assignments;
  • engagement and consistency signals;
  • teacher-assigned learning activities;
  • intervention/support notes with appropriate access control;
  • comparison of a student's current performance with their own previous performance;
  • class-level and group-level patterns where appropriate;
  • actionable next steps for educational support.

Important: analytics must show evidence and actionable educational information. Do not convert learning data into unsupported psychological, medical, intelligence or personality judgements.

12. Teacher Command Center

Teachers should not have to manually inspect every student record.

The system should surface useful signals:

  • students who have not practiced recently;
  • weak topics;
  • persistent error patterns;
  • assigned work;

  • mastery development;
  • students requiring pedagogical attention.

13A. NON-NEGOTIABLE — IDSS EGE IS A CANONICAL RAG SYSTEM

THE IDSS EGE WEB APP MUST BE ARCHITECTED AS A CANONICAL KNOWLEDGE BASE + RETRIEVAL-AUGMENTED GENERATION (RAG) SYSTEM.

The application is not a generic AI tutor that happens to contain exam material. Its academic intelligence must be grounded exclusively in the current authoritative CANON contained in the repository https://github.com/IDSS123a/IDSS-EGE-EKSTERNA.

CANONICAL CONTENT IS THE KNOWLEDGE BOUNDARY. For current exam preparation, the system may retrieve, explain, transform, combine or generate learning experiences only from information that is traceable to the currently active canonical sources. Generic model knowledge, internet knowledge, assumptions, hallucinated content and uncited AI knowledge must never silently enter the academic knowledge base.

CATALOGUE QUESTION UNIVERSE — MANDATORY

For each of the three prescribed subjects — Bosnian language, Mathematics and German language — the canonical catalogue is the authoritative question universe for the exam-preparation engine. The system must therefore ingest and structurally understand the complete catalogue question set supplied by the current CANON.

The initial implementation must process at least 200 catalogue questions per subject where the current official catalogue contains at least that many questions. If the authoritative catalogue contains a different number, the system must ingest the complete authoritative set rather than inventing or padding questions to reach an arbitrary number.

NO EXAM QUESTION MAY BE INVENTED. A question presented as an official/canonical exam question must resolve to an exact canonical source record. If the application generates a practice variant, it must be explicitly labelled as a derived practice item, linked to the source catalogue question(s), and must never be represented as an official catalogue question.

        ↓

        ↓

        ↓

Every retrieval operation must be constrained by the active canonical version and applicable subject/scope. Retrieval must never search across superseded versions unless a historical/audit operation explicitly requests them.

Syntax → Logic → Semantics: mandatory question understanding

ACA must not treat catalogue ingestion as simple PDF-to-text extraction. Every catalogue question must be converted into a structured knowledge object that preserves its meaning.

  • Syntax: exact original wording, sentence structure, operators, numbers, symbols, punctuation, answer choices, tables, diagrams, blanks and other structural elements.
  • Logic: what the question asks the learner to do; constraints; relationships; operations; conditions; expected response type; scoring-relevant structure where CANON provides it.
  • Semantics: subject meaning, topic, competency, concept, skill, prerequisite knowledge and intended learning/exam construct, strictly grounded in the source.
  • Provenance: source document, document version, page/section, question identifier, extraction status, validation status and reviewer/audit trail.

The system must retain the original source representation alongside the normalized representation so that an administrator or teacher can always inspect what was actually published.

RAG SAFETY RULES — ZERO TOLERANCE
  • Never answer an academic question as CANONICAL unless the answer can be traced to an active canonical source.
  • Never use a superseded catalogue or regulation as current content.
  • Never mix versions of a catalogue inside one current learning experience.
  • Never allow an LLM to overwrite canonical source text with its own paraphrase.
  • Never store an AI-generated explanation as if it were an official ministry statement.
  • Never generate an “official catalogue question” from model knowledge.
  • Never silently fill a missing or ambiguous source with general knowledge.
  • If evidence is insufficient, the system must say that the canonical source does not provide enough information and route the item for review.

26. Success Criteria

IDSS EGE is successful when all of the following are true:

  1. The application is demonstrably grounded in the actual repository sources.
  2. The student preparation scope is exactly the three prescribed subjects: Bosnian language, Mathematics and German language, subject to the current CANON.

  4. The Director / Superadmin can replace an active canonical catalogue, law, regulation, rulebook, official form or other supported authoritative document through the control panel without changing application code.

  6. Canonical-dependent content, indexes and caches are refreshed so the current active source actually drives the application.
  7. All catalogue questions from the current canonical subject documents are ingested and structurally/semantically validated, with at least 200 per subject where the source provides that quantity.
  8. Official-format documents and exports have a documented canonical source and verification status.
  9. Students can enter the system and immediately understand what to do next.
  10. Daily preparation is engaging enough to encourage repeated voluntary use.
  11. Practice and mock exams are based on validated exam information.
  12. Teachers can identify useful learning signals without manually processing raw data.
  13. School leadership has appropriate aggregate visibility and control.
  14. Authorization prevents users from accessing data outside their role.
  15. Every user authenticates through the defined username/password flow and sensitive authorization is enforced server-side.
  16. The platform preserves longitudinal student history across school years while respecting privacy and cohort boundaries.
  17. The first-paint splash appears before the main application experience, uses the official IDSS logo and rotates at least 10 student motivational messages.
  18. Security testing demonstrates meaningful protection against common application threats; the product makes no false claim of absolute security.
  19. Gamification motivates learning without corrupting academic meaning.
  20. The application remains maintainable and testable.
  21. Existing valuable prototype functionality is preserved or deliberately improved.
  22. The product is deployable and operational—not merely a visual prototype.
